# Команды и рабочие сценарии

[Документация](README.md) · [English](../en/usage.md)

Примеры используют стандартный каталог данных. Для другого общего каталога добавьте `--data-dir /path/to/data`. Глобальные параметры, например `--data-dir`, `--verbose` и `--yes`, можно указывать до или после команды. Для навигации используйте `dotm help`, для вложенной справки — `dotm help files`, для синтаксиса команды — `dotm <command> --help`. Справка компактно сгруппирована; примеры приведены у соответствующих команд.

## Дополнение команд оболочки

Сгенерируйте скрипт автодополнения в stdout встроенной командой Cobra. dotm не устанавливает скрипты и не меняет файлы запуска оболочки. Примеры подключения доступны через `dotm completion bash --help` (подставьте имя своей оболочки):

```sh
dotm completion bash > dotm.bash
dotm completion zsh > dotm.zsh
dotm completion fish > dotm.fish
dotm completion powershell > dotm.ps1
```

Для временного сеанса Bash или Zsh загрузите скрипт непосредственно:

```sh
source <(dotm completion bash)
source <(dotm completion zsh)
```

Для постоянного использования поместите сгенерированный скрипт в каталог дополнений оболочки и настройте его загрузку по её правилам (например, completion.d для Bash или `$fpath` вместе с `compinit` для Zsh). Для Fish и PowerShell также используются стандартные расположения и механизмы загрузки скриптов завершения. Выберите пользовательский каталог по документации своей оболочки; dotm не вносит постоянных изменений в настройки оболочки.

## Вывод и подробный режим

Справка, результаты, предупреждения, ошибки и запросы подтверждения dotm написаны на простом техническом английском. Имена команд, флагов, полей конфигурации и значений статуса сохраняют технические названия. Вывод внешних инструментов и пользовательских хуков показывается без изменений.

По умолчанию изменяющие команды `install`, `update` и `remove-extras` сообщают о пакетных эффектах, наблюдавшихся именно в этом запуске, а не обо всём установленном наборе. При отсутствии изменений пакетов это явно указывается; неизменившийся инвентарь доступен только с глобальным `-v` / `--verbose`. Конфигурационная работа даёт одну общую сводку завершения/ошибки без шаблонных сообщений об успехе каждого приложения; указываются изменённые пути назначения и изменения источника, а неизменившиеся успешные пути и успешные исключения по правилам игнорирования остаются в подробном отчёте. Завершённый цикл конфигурации или запуск хуков не означает, что файлы изменились. Подробный режим добавляет детали:

```sh
./dotm install --verbose
./dotm -v status
./dotm -viur
```

Метки успеха, предупреждения и ошибки подсвечиваются только в терминале; `NO_COLOR` отключает цвет. При перенаправлении escape-последовательностей цвета нет. Ошибки, предупреждения, блокирующие зависимости, сохранённые резервные копии, частичные эффекты и фактический вывод нативных команд/хуков видны и без `--verbose`. `status`, `show`, `configs`, `apps`, `doctor` и команды lint/check сохраняют запрошенное состояние или результаты проверок; подробный режим лишь добавляет детали. Готовность пакетов не доказывает синхронизацию конфигурации.

## Справочник команд

| Команда | Действие |
| --- | --- |
| `configs` | Список конфигураций и прямых выборок; локальный выбор и Nix не нужны |
| `apps` | Каталог приложений, зависимости, пакеты, цели и пути хуков; локальный выбор и Nix не нужны |
| `show` | Локальный выбор, приложения после раскрытия зависимостей, уникальные пакеты и владельцы целей; Nix не нужен |
| `status` | Просмотр пакетов и готовности без изменений; не проверяет содержимое файлов |
| `install` | Хуки, установка недостающих желаемых пакетов, синхронизация готовых конфигураций |
| `update` | Продвижение источника, обновление установленных желаемых приложений и полного набора их логических зависимостей; синхронизация всех готовых желаемых конфигураций |
| `update cfg` | Синхронизация готовых конфигураций без пакетной работы и пакетных pre-хуков; одна общая сводка конфигурации, без инвентаря пакетов |
| `cfg lint [--source /absolute/checkout]` | Пассивная локальная проверка исходников/настроек; манифесты, выбор, Nix и бинарный файл chezmoi не нужны |
| `files lint` | Проверка деклараций, действующих нативных правил и подключения опубликованной политики |
| `files refresh [--update-source]` | Подготовка, проверка и публикация политики; получение/обновление исходников — только с явным флагом |
| `files status` | Локальное обновление политики и инвентаризация изменений/неклассифицированных файлов; без загрузки исходников |
| `remove-extras [--yes]` | Удаление явно одобренного лишнего с защитой желаемых/общих дескрипторов |
| `init [--configuration NAME] [--repository URL]` | Подготовка входных данных, установка отсутствующего выбранного chezmoi/зависимостей, настройка source/интеграции/политики; без применения файлов назначения |
| `doctor` | Диагностика dotm/source/политики, бэкендов, хоста и текущего сеанса без исправлений |
| `clean [--keep N] [--gc] [--dry-run] [--yes]` | Отдельная очистка истории и необязательная сборка мусора общего хранилища; манифесты и выбор не нужны |

Команды `files` вычисляют доверенные шаблоны, но не применяют конфигурации, не запускают хуки приложений и не проверяют Nix. См. [chezmoi и файлы](chezmoi.md).

## Инициализация dotm

`init` настраивает уже работающий dotm, но не устанавливает его исполняемый файл. Заранее подготовьте Nix/Git. Отсутствующий chezmoi объявляется в каталоге, выбирается в текущей конфигурации и устанавливается только со своим замыканием зависимостей; пользовательские объявления сохраняются. Совместимые внешние исполняемые файлы используются без автоматического выбора/присвоения. См. [установку](installation.md#инициализация-dotm).

Укажите `--configuration` и `--repository`, если локальные данные не задают однозначный выбор. Глобальный `--data-dir` выбирает общие манифесты, а не локальные настройки машины. Init проверяет локальные входные данные и пути до записей и отдельно запрашивает согласие на изменения локальных намерений и замену источника. Обхода через `--yes` нет: отмена/EOF безопасно прерывает операцию.

Init подготавливает одобренные файлы, бэкенд, checkout, совместимые статические настройки, корневую интеграцию ignore и политику, затем проверяет обычное обнаружение. Совпадающий checkout проверяется без fetch/fast-forward; локальные изменения и нативные правила сохраняются. Устанавливаются только отсутствующие chezmoi и зависимости с их пакетными pre-хуками; остальные выбранные приложения, конфигурационные хуки и файлы назначения не развёртываются. Автокоммитов и молчаливой смены origin нет. Небезопасная интеграция требует ручного исправления. Проверьте завершённые изменения манифестов/пакетов/источника и резервные копии, затем самостоятельно закоммитьте общие манифесты и checkout. Поздние ошибки сохраняют ранние эффекты; после исправления повторите настройку.

Если init меняет интеграцию в checkout, он явно просит проверить и закоммитить изменения, включая `.chezmoiignore`, до синхронизации источника. Напоминание появляется и при ошибке более позднего этапа настройки. Обычные `install`, `update`, `update cfg` и `files refresh --update-source` требуют чистого источника; разрешение init подготавливать изменённый совпадающий checkout это правило не ослабляет.

## Диагностика настройки

Запускайте `./dotm doctor` после настройки или при ошибках предварительных условий; глобальный `--data-dir` выбирает общие манифесты. Проверяются выбор/декларации, пассивная безопасность source/настроек, собственная корневая интеграция, действующие нативные правила и привязка/актуальность опубликованной политики, возможности Git/chezmoi, features/daemon/профиль Nix и текущие PATH/XDG. Независимые проверки продолжаются после ошибок; заблокированные проверки называют недостающую предпосылку и не считаются успешными.

Doctor не устанавливает пакеты, не выполняет fetch или recovery пакетов, не меняет постоянные настройки/source/политику/профиль, не запускает хуки приложений и не применяет файлы назначения. Флага `--fix` нет. Действующие правила проверяются с вычислением доверенных шаблонов без изоляции их кода; временные пробы удаляются. Нативная проверка Nix может создавать вспомогательное runtime/cache-состояние. Действительно отсутствующий профиль первого запуска — информационное состояние, не аналог повреждённого профиля или оборванной ссылки. Проверки сеанса описывают только текущий процесс, не новый login или графический сеанс.

Ошибки появляются один раз в stderr; предупреждения, результаты и заблокированные проверки идут в stdout. Код 0 означает отсутствие ошибочных результатов, 1 — ошибки проверенных входных данных dotm/source/политики, 3 — ошибки хоста/выполнения/внутренние ошибки; сохраняется максимальная серьёзность. Рекомендации различают настройку через `init`, регенерацию через `files refresh`, явное исправление входных данных и внешнюю подготовку хоста/сеанса. Doctor не устанавливает Nix и не настраивает сеанс.

## Просмотр и установка

```sh
./dotm show
./dotm status
./dotm install
./dotm status
```

Статус различает установленные, частичные, отсутствующие и беспакетные приложения, готовность зависимостей и удаляемое лишнее. `status --verbose` показывает явные нативные записи, дескрипторы, URL источников и store paths. Готовность конфигурации учитывает полное замыкание зависимостей; это не отметка об установке и не доказательство синхронизации файлов.

При исправном источнике установка добавляет только недостающие дескрипторы, включая части многопакетных приложений. Установленное, лишнее и lock источника сохраняются. Повторная установка уже полного набора всё равно выполняет настроенные хуки/конфигурационные стадии; по умолчанию пакетный отчёт сообщает, что пакеты не изменились, а не повторяет инвентарь установки. Сводка конфигурации описывает цикл и при сообщении изменений показывает фактически применённые пути/изменения источника, не подразумевая изменений файлов только из-за завершения цикла или хуков. Неоднозначные желаемые записи приводят к ошибке, а не автоматическому исправлению.

## Обновление

```sh
./dotm update
# Повторить только конфигурационную часть:
./dotm update cfg
```

Обновление продвигает локальную фиксацию `nixos-unstable`. Область определяется активными пакетными записями: частичные приложения дополняются, включаются все текущие компоненты и транзитивные логические спутники, в том числе недавно добавленные. Общий активный дескриптор может свидетельствовать о частичной установке нескольких приложений. Установленный спутник не выбирает отсутствующего родителя; полностью отсутствующие независимые приложения остаются для `install`. Одни неактивные записи не запускают обновление. Лишнее сохраняет версии. Без установленных желаемых приложений пакетная часть ничего не делает, но готовые конфигурации всё равно обрабатываются.

Изменения lock и путей пакетов в store выводятся отдельно: новая ревизия источника не обязана менять версии пакетов. По умолчанию update сообщает только о пакетных эффектах этого запуска и явно указывает, если пакеты не изменились; неизменившийся инвентарь доступен только с `-v` / `--verbose`. Ошибки пакетной части/источника запускают восстановление; поздние конфигурационные ошибки сохраняют успешные пакетные изменения. См. [восстановление](troubleshooting.md).

## Смена конфигурации и удаление лишнего

Измените `configuration` в локальном `config.toml`, проверьте `show`/`status`, затем выполните `install`. Сам выбор не удаляет пакеты и файлы назначения. Для лишних пакетов:

```sh
./dotm remove-extras
# Явно одобрить все удаления без вопросов:
./dotm remove-extras --yes
```

Каждое лишнее приложение подтверждается отдельно. Желаемые/общие компоненты защищены; общий компонент лишних приложений удаляется только при одобрении всех использующих его приложений. Неизвестные/внешние и неактивные записи желаемых дескрипторов рассматриваются отдельно. `y`/`yes` — согласие, Enter или `n`/`no` — отказ, `q`/`quit` — отмена. EOF/ошибка ввода отменяет весь собранный план; перенаправленный ввод должен содержать полную строку для каждого вопроса. Перед одним нативным пакетом удалений состояние проверяется повторно.

Удаление не меняет lock, не сокращает историю, не удаляет объекты store и не отменяет действия над пользовательскими данными. Нативная ошибка может оставить частичный результат; выводится фактическое состояние без автоматического отката/повтора.

Chezmoi — обычное выбранное приложение: оно обновляется в выбранной области и становится удаляемым, когда больше не требуется прямо или совместно. Install/update находят и проверяют текущий бинарный файл профиля после пакетной части, используя новую версию даже без профиля в PATH. Несовместимость бэкенда останавливает конфигурационную работу, сохраняя успешные пакетные изменения.

## История и место на диске

```sh
./dotm clean --dry-run
./dotm clean
./dotm clean --keep 1 --gc
```

По умолчанию остаются активное поколение и два **других** с наибольшими номерами. `--keep N` меняет число дополнительных поколений; `--keep 0` удаляет все альтернативы отката. После отката альтернативы могут быть новее активного поколения. Очищается история только стандартного XDG-профиля.

Без `--gc` удаление корней истории может не освободить место пакетов. **`--gc` разрешает сборку мусора во всём общем store, включая посторонние сборки и кеши без корней.** Активный/сохранённые профили и другие GC roots защищают свои объекты. `--dry-run --gc` показывает мусор при текущих корнях, а не дополнительный мусор, который появится после удаления истории.

Ответы подтверждения такие же, как для удаления; `--yes` обходит вопрос, а изменение истории отменяет одобренный план. Ошибки не восстанавливают уже удалённую историю автоматически. Нативный откат к сохранённому поколению описан в [устранении проблем](troubleshooting.md).

## Совмещение операций

```sh
./dotm -iur
./dotm -iur --yes
```

`-i`/`--install`, `-u`/`--update`, `-r`/`--remove-extras` допускают группировку или отдельные флаги. Порядок всегда **update → install → remove-extras**, каждая выбранная операция выполняется один раз независимо от порядка/повторов флагов. Не смешивайте их с подкомандой. `--yes` требует удаления или отдельного `clean` и никогда не подтверждает замену исходников. Очистка не включается.

Манифесты/выбор читаются один раз, но каждая операция заново проверяет пакеты. Установка и обновление сохраняют отдельные циклы хуков/конфигураций. Конфигурационные ошибки допускают следующие операции; ошибки пакетов/pre-хуков/внутренние ошибки останавливают последовательность. Сохраняется максимальный код ошибки; предыдущие изменения не отменяются. Другой порядок задавайте отдельными командами через `&&`.

## Параллельность и вывод

На один пользовательский XDG state-каталог разрешена одна изменяющая операция: `init`, `install`, `update`, `update cfg`, `files refresh`, `files status`, `remove-extras` и `clean` без dry-run сразу завершаются ошибкой при занятой блокировке. Комбинация держит её во время вопросов и хуков. Вложенная изменяющая команда из хука не ждёт, а завершается ошибкой. Чтение и dry-run очистки доступны, но не дают атомарного снимка.

Приватные файлы Linux flock находятся в `/tmp/dotm-<uid>/`; не удаляйте их во время возможной работы процессов. Нативные дочерние процессы update/add/recovery сохраняют владение после гибели dotm; хуки — нет, поэтому остановите оставшиеся хуки перед повтором. Прямые изменения Nix/Git/chezmoi не координируются, как и разные state-каталоги с одним источником.

stdout содержит просмотр и фактические результаты операций; stderr — диагностику стадий и вывод нативных команд/хуков. Ненулевой код возможен после успешных изменений пакетов или файлов. См. [коды и повтор](troubleshooting.md).
