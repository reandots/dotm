## Подготовка рабочего дерева

Установите [mise](https://mise.jdx.dev/) и [just](https://just.systems/), затем из корня репозитория выполните:

```sh
just setup
```

Рецепт явно доверяет `mise.toml` этого рабочего дерева, устанавливает закреплённые версии инструментов и загружает зависимости Go с помощью закреплённой версии Go. **Предупреждение о доверии:** выполняйте команду только для репозитория, конфигурации которого вы доверяете: `mise trust mise.toml` разрешает использование конфигурации инструментов этого проекта. Подготовку можно безопасно повторять; при первой ошибке выполнение останавливается. Команда не активирует mise в оболочке и не запускает проверки проекта. Для установки нужны сеть и доступ на запись к каталогам данных, состояния и кэша mise; загрузка зависимостей также требует сети и доступного для записи кэша Go. Если песочница запрещает запись, выполните подготовку вне неё или предоставьте необходимый доступ к файловой системе.

В `mise.toml` закреплены Go 1.27.4, golangci-lint 2.15.0, gopls v0.24.0 и Delve 1.27.2. Отдельно `go.mod` объявляет `go 1.23.0` — это базовая версия языка и инструментария для совместимости модуля, а не выбранная для разработки версия Go. Для команд проекта используйте закреплённую версию Go. Если mise активирован в оболочке, запускайте `just <рецепт>`; иначе используйте `mise exec -- just <рецепт>`, чтобы не задействовать случайно глобальные версии инструментов.

## Инструменты редактора

gopls и Delve используются редактором для навигации по коду и отладки; это не дополнительные проверки перед коммитом. Для VS Code предоставьте расширению Go доступ к shim-файлам mise или используйте [интеграцию mise с VS Code](https://mise.jdx.dev/ide-integration.html#vs-code), затем проверьте выбор инструментов командой **Go: Locate Configured Go Tools**. После смены версий перезапустите затронутые инструменты. Репозиторий не переопределяет пользовательские настройки VS Code.

## Рецепты

Выполните `just`, чтобы вывести список команд.

| Рецепт | Назначение |
| --- | --- |
| `just setup` | Доверить конфигурацию mise рабочего дерева, установить закреплённые инструменты и загрузить зависимости Go. |
| `just fmt` | Форматировать исходники Go на месте настроенным форматтером gofumpt. |
| `just fmt-check` | Проверить форматирование без изменения исходников; при ошибке вывести diff. |
| `just vet` | Запустить `go vet ./...`. |
| `just lint` | Запустить закреплённый golangci-lint без изменения исходников и файлов модулей. |
| `just lint-fix` | Применить поддерживаемые исправления линтера на месте. |
| `just test` | Запустить все тесты Go командой `go test ./...`. |
| `just mod-check` | Проверить актуальность файлов модуля без изменения `go.mod` и `go.sum`. |
| `just build` | Собрать локальный бинарный файл `./dotm`; установка не выполняется. |
| `just build-release` | Собрать тот же `./dotm` с `-ldflags="-s -w"`, исключив отладочные символы и данные DWARF. |
| `just run --data-dir examples apps` | Запустить CLI, передав ему аргументы после имени рецепта. |
| `just precommit` | Последовательно запустить `lint`, `test` и `build`; при ошибке остановиться. |

Рецепты форматирования и линтинга напрямую вызывают golangci-lint и используют общие настройки `.golangci.yml`, в том числе gofumpt, ограничение строк в 120 символов и явно выбранные анализаторы govet. Проверки распространяются и на тестовый код, а загрузка модулей работает в режиме только для чтения. `fmt-check` и `lint` не меняют исходники; `fmt` и `lint-fix` меняют. `precommit` не запускает `fmt`, `vet` или `mod-check`, не устанавливает Git-хук и не переписывает исходники или файлы модулей. При необходимости запускайте `just mod-check` отдельно. Для намеренного изменения зависимостей явно выполните `go mod tidy` и добавьте полученные изменения файлов модуля. Release-сборка предназначена для получения бинарного файла меньшего размера, когда отладка по символам не требуется; обычная разработка и precommit используют `just build`.

## Архитектура

Точка входа приложения — `main.go`: она передаёт аргументы и стандартные потоки в `internal/cli.Run`, выводит ошибки и преобразует их в коды завершения CLI. Пакеты `internal/` разделены по обязанностям:

- `cli` — разбор команд и организация пользовательских операций.
- `manifest` — чтение и разрешение описаний файлов в манифесте.
- `installed` — конфигурация установленного состояния, состояние источников, операции установки, обновления, удаления и очистки, а также восстановление.
- `chezmoi` — инвентаризация исходников chezmoi, политики, проверка корректности и применение.
- `hooks` — общие пути и поддержка хуков.
- `pathutil` — общие утилиты для работы с путями.

Размещайте повторно используемую логику предметной области в соответствующем внутреннем пакете, а обработку аргументов и команд CLI — в `internal/cli`. Примеры в `examples/` содержат образцы каталогов и конфигураций, но не заменяют тесты.

## Тесты и соглашения разработки

Тесты располагаются рядом с проверяемым пакетом. Следуйте принятому шаблону `testify/suite`: suite встраивает `suite.Suite`, функция верхнего уровня `Test…Suite(t *testing.T)` вызывает `suite.Run`, а наборы табличных случаев используют подтесты suite. Используйте `s.Require()` для предварительных условий, после нарушения которых продолжать тест небезопасно, и обычные suite-утверждения для независимых результатов. Сосредоточьтесь на сложной логике, границах с повышенным риском ошибок и значимых регрессиях, а не на тривиальных деталях или целевом проценте покрытия.

Некоторые тесты восстановления состояния источников в `installed` используют поддельные исполняемые файлы Nix, реализованные на Python 3. Перед запуском `go test ./internal/installed` или всего набора тестов убедитесь, что `python3` доступен через `PATH`. Эти фикстуры не изменяют настоящий профиль или хранилище Nix. Для исполняемых тестовых фикстур нужны права только владельца и, где требуется, документированные локальные исключения линтера; точные правила приведены в [стандартах базы знаний](../../.agent/development.md). Линтинг и форматирование должны применяться также к тестам и сгенерированным файлам; не добавляйте общие исключения для тестов.

Перед отправкой изменений запустите относящиеся к ним проверки и обычно `just precommit`; отдельно рассмотрите `just fmt-check` и `just mod-check`, поскольку они не входят в этот рецепт. Не указывайте проверки, которые фактически не запускались. При изменении поведения, команд, требований к подготовке или настроек обновляйте применимую публичную документацию **на обоих языках** (`doc/en/` и `doc/ru/`) и поддерживайте краткое английское описание и ссылки в корневом README. Руководства на двух языках должны охватывать одинаковые темы. [База знаний](../../.agent/development.md) предназначена для подробностей, нужных участникам разработки; публичное описание поведения размещайте в публичной документации.
